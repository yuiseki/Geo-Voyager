# ローカル LLM はハーネスを理解しているか（確かめ）

2026-10-10。Goal をまたいで Skill library を持ち越した 1 周（[adaptive_shared_library.md](adaptive_shared_library.md)）で、本体が同じで名前だけ違う Skill が増えた。お嬢様の仮説は「モデルがこのハーネスを理解できていない」。直す前に、モデルが何を理解しているかを確かめた。

## 方法

`bench/probe_harness_understanding.py`。Generator が実際に送るプロンプト（Intent「港区内の amenity=hospital の地物数」、対象は港区 relation_id 1761717、持ち越した Library から `get_osm_relation_id` と `count_osm_amenity_cafe` を見せる）を、そのままローカル LLM に渡した。最後の依頼だけを、コードの代わりに 5 つの質問に答えさせるものに替えた。3 回。生成時と同じ設定（temperature 0.2、thinking あり）。記録は [evidence/harness_understanding/probe1.json](evidence/harness_understanding/probe1.json)（プロンプトと回答の全文）。

正しい理解（今の実装）:

- Q1 実行: 実行環境が最後の関数を、引数の名前に合う実行時の値（`intent_target`、`previous_observations`、`dataset_id`、`intent_text`）で呼び、戻り値を JSON で出力する。
- Q2 見せた Skill: 保存済みの関数で、実行時に定義済み。import も定義も不要で、名前で呼べる。
- Q3 成功した後: 関数はその名前で Skill として保存され、後の Intent の生成のときに検索で見せられ、そこから名前で呼ばれる（引数を変えて）。
- Q4 条件の渡し方: 実行環境が渡すのは上の 4 つだけ。タグなどの条件は既定値つきの引数にし、既定値に今回の値を書く。後の Intent の関数は、その引数に別の値を渡して呼ぶ。
- Q5 この Intent: `count_osm_amenity_cafe` はタグが中に書き込まれているので使えない。新しい関数を書くのが正しい（できれば汎用に）。

## 結果

| 質問 | 3 回の答え | 判定 |
|---|---|---|
| Q1 実行 | 3 回とも、実行環境が `intent_target` を渡して関数を呼び、戻り値が JSON で出力される、と答えた | 理解している |
| Q2 見せた Skill | 3 回とも、保存済みで定義済み、import も定義も不要で名前で呼べる、と答えた。`count_osm_amenity_cafe` はタグが cafe に固定なので使えない、とも答えた | 理解している |
| Q3 成功した後 | 3 回とも、関数が Skill として保存され、後の Intent に見せられることに触れなかった。1 回は「後の Intent は、直接関数を部品として呼び出すことはできない」と答えた | 理解していない |
| Q4 条件の渡し方 | 2 回は「既定値つきのキーワード引数」と答えたが、誰がその値を渡すかは曖昧（「呼び出し側または実行環境のラッパーが渡す」）。1 回は「条件を引数として渡すことは想定されていない」と答えた | 曖昧、または誤り |
| Q5 この Intent | 3 回とも「新しい関数を書く」。理由も正しい（cafe に固定されている） | 理解している |

## 分かったこと

- モデルは、自分の関数がどう呼ばれるか（Q1）と、見せた Skill が名前で呼べること（Q2）は理解している。それでも実際の生成では書き写すことが多いので、知識と振る舞いの間にずれがある。
- 理解していないのは、自分の関数のその後（Q3）と、条件を関数に渡す仕組み（Q4）である。モデルにとって、今書く関数は「この Intent のための使い捨て」で、後で別の Intent から引数を変えて呼ばれる部品だ、という前提が伝わっていない。名前に区やタグを入れる、タグを中に書き込む、という増殖の振る舞いと合っている。
- プロンプトには、Q3 と Q4 の答えにあたる説明が実際に無い（規則 4 の「関数は後で別の Intent から部品として呼ばれる」の 1 文だけ）。プロンプトは約 8,600 文字で、ハーネスの規則は 7,027 文字目から始まる。
- 1 回の答えには、以前からある規則「キー・値をコードに固定しない」と、既定値に今回のタグを書くことが衝突する、という読み方が出た（Q5 の理由）。

## 次の一手（案）

プロンプトの先頭に、ハーネスの短い説明を置く: (1) 関数の一生（成功すると関数名で保存され、後の Intent に見せられ、引数を変えて呼ばれる）、(2) 引数の仕組み（実行環境が渡す 4 つの値と、既定値つき引数で条件を受け取ること）、(3) 保存済みの Skill を新しい関数が引数を変えて呼ぶ小さな実例。そのうえで同じ確かめを流し、Q3 と Q4 の答えが正しくなるかを見る。

## 説明を書き直した後の確かめ（2 回目）

Generator のプロンプトの先頭に「この環境の仕組み」を置いた（`harness_section`）: 関数の一生（成功すると関数名で Skill として保存され、後の別の Intent に見せられ、引数を変えて呼ばれる）、この Intent で実行環境が渡す値、条件を既定値つきの引数で受け取り既定値に今回の値を書くこと、対象の名前や条件を関数名や中身に書き込まないこと、保存済みの Skill を新しい関数が引数を変えて呼ぶ実例。タグ探索の規則「キー・値をコードに固定しない」には、Intent が条件を明示しているときは既定値に書いてよい、と添えた。単体テスト 849 件。

同じ 5 問を 3 回（[evidence/harness_understanding/probe2.json](evidence/harness_understanding/probe2.json)）:

| 質問 | 1 回目（書き直し前） | 2 回目（書き直し後） |
|---|---|---|
| Q3 成功した関数はその後どうなるか | 0 / 3 | 3 / 3（関数名のまま Skill として保存され、後の Intent に候補として見せられ、引数を変えて呼ばれる） |
| Q4 条件を関数にどう渡すか | 曖昧 2、誤り 1 | 3 / 3（既定値つきの引数で受け取り、後の Intent が別の値を渡して呼ぶ） |

答えが変わったことは、説明が読まれたことを示すが、生成の振る舞いが変わるかは別である（Q2 では知識と振る舞いがずれていた）。持ち越しの 1 周を流し直して確かめる。
